## 핵심 개념 상세 정리

### 8-1. LangGraph 기초 — State, Node, Edge

LangChain은 직선형(chain) 흐름 → LangGraph는 분기/루프가 가능한 그래프 구조.

#### 구성 요소

| 요소 | 역할 | 비유 |
|---|---|---|
| Node | 함수 (search, find, ...) | 지하철 역 |
| Edge | 노드 간 연결선 | 선로 |
| State | 그래프 전체 공유 딕셔너리 | 승객이 들고 다니는 가방 |

#### 기본 흐름

```
State 정의(TypedDict) → Node 함수 정의 → StateGraph에 등록 → Edge 연결 → compile → invoke
```

```python
class MiniState(TypedDict):
    text: str

def upper_node(state):
    return {'text': state['text'].upper()}

b = StateGraph(MiniState)
b.add_node('upper', upper_node)
b.add_edge(START, 'upper')
b.add_edge('upper', END)
app = b.compile()
app.invoke({'text': 'hello'})
```

> 실무: Node 함수는 변경된 키만 리턴해야 함. 전체 state를 리턴하면 그래프가 커질 때 문제 발생

### 8-2. State 설계 — TypedDict & 키 전략

- State 설계가 그래프의 70% 이상을 차지
- TypedDict로 타입 명시 → 노드 간 데이터 계약

```python
class ChatState(TypedDict):
    user_msg: str
    reply: str
    turn: int
```

### 8-3. 조건부 분기 — add_conditional_edges

- `add_conditional_edges(이전노드, 라우터함수, 매핑dict)` 형태
- 라우터 함수의 반환 문자열 키에 따라 다음 노드 결정
- START에서 직접 분기 불가 → 더미 노드(`start_n`)를 앞에 배치

```python
def parity_router(state) -> str:
    return 'even' if state['n'] % 2 == 0 else 'odd'

b.add_conditional_edges('start_n', parity_router,
                        {'even': 'even_handler', 'odd': 'odd_handler'})
```

> 실무: 분기 후 모든 경로가 하나의 merge 노드로 합류하면 공통 후처리(접미사, 로깅 등) 가능

### 8-4. Reducer & Annotated — 상태 누적 전략

기본 동작: 노드가 키를 반환하면 덮어쓰기 → `Annotated`로 커스텀 누적 로직 적용 가능.

| 리듀서 | 동작 | 용도 |
|---|---|---|
| `operator.add` | 리스트 이어붙이기 | 이벤트 로그 누적 |
| `add_messages` | 메시지 히스토리 누적 + ID 기반 업데이트 | 대화 관리 |
| `keep_max` | 최대값만 유지 | 최고 점수 |
| `add_int` | 정수 합산 | 누적 점수 |
| `merge_dicts` | 딕셔너리 병합 | 메타데이터 수집 |

```python
class AccumState(TypedDict):
    msgs: Annotated[list, operator.add]
```

### 8-5. 메시지 관리 — add_messages, RemoveMessage

- `add_messages`: `operator.add`와 유사하지만, 같은 ID 메시지는 최신 것으로 교체
- `RemoveMessage(id=m.id)`: 특정 메시지 삭제
- 컨텍스트 트리밍: 최근 N개 메시지만 유지하여 토큰 절약

```python
class TrimState(TypedDict):
    messages: Annotated[list, add_messages]

def trim_node(state):
    msgs = state['messages']
    to_remove = msgs[:-N]
    return {'messages': [RemoveMessage(id=m.id) for m in to_remove]}
```

### 8-6. ReAct 패턴 — Reasoning + Acting

2022년 프린스턴+구글 논문(Yao et al.)에서 제안. LLM이 "생각 → 도구 사용 → 관찰 → 다시 생각" 루프로 복잡한 문제 해결.

```
START → agent → tool_calls 있음? → tools → agent → ... → END
                  ↓ 없음
                 END
```

### 8-7. ToolNode & tools_condition — 내장 자동 탐지

직접 구현 vs 내장 함수 비교:

| 직접 구현 | 내장 |
|---|---|
| `tools_node()` 함수 작성 | `ToolNode(tools)` |
| `should_continue()` 함수 작성 | `tools_condition` |

```python
b.add_node('tools', ToolNode(tools))
b.add_conditional_edges('agent', tools_condition)
```

### 8-8. MemorySaver — thread_id별 대화 기억

- `MemorySaver`를 checkpointer로 전달하면 thread_id별 대화 기억 유지
- 같은 thread_id → 이전 대화 이어감, 다른 thread_id → 새 대화 시작

```python
memory = MemorySaver()
mem_app = b2.compile(checkpointer=memory)
cfg = {'configurable': {'thread_id': 'alice'}}
```

### 8-9. 상태 스냅샷 — get_state, get_state_history, update_state

| 메서드 | 용도 |
|---|---|
| `get_state(config)` | 현재 스냅샷 — values, next, config 등 |
| `get_state_history(config)` | 전체 실행 이력 (시간 역순) |
| `update_state(config, values)` | 그래프 실행 없이 state 직접 주입 |

- `invoke(None, config)`: 새 입력 없이 현재 state에서 이어서 실행
- 디버깅, 시나리오 재현에 유용

### 8-10. HITL — interrupt_before, 도구 승인/거부

에이전트가 되돌리기 어려운 행동(API 호출, 결제 등) 전에 사람의 승인을 받는 패턴.

```
사용자 질문 → agent(LLM) → tool_calls 결정
                              ↓
                ⛔ interrupt_before=['tools'] → 멈춤
                              ↓
                사람 확인 → pending tool_calls 검토
                              ↓
                승인: invoke(None) → tools 실행 → 최종 답변
                거부: update_state로 거부 메시지 주입
```

```python
hitl_app = b2.compile(checkpointer=MemorySaver(), interrupt_before=['tools'])
```

> 실무: `interrupt_before`에 어떤 노드든 넣으면 해당 노드 실행 직전에 중단됨

## 코드 흐름 정리

```
[1차시: LangGraph 기초]
State 정의 → Node 함수 → StateGraph 조립 → compile → invoke
    │
    ├── 직렬: add_edge(A, B)
    └── 분기: add_conditional_edges(노드, 라우터, 매핑)

[2차시: Reducer · 메시지]
Annotated[타입, 리듀서] → 덮어쓰기 대신 누적
    │
    ├── operator.add → 리스트 이어붙이기
    ├── add_messages → 메시지 히스토리 관리
    └── 커스텀(keep_max, merge_dicts) → 용도별 누적

[3차시: Agent · 메모리 · HITL]
agent_node → should_continue → tools_node → agent_node → ...
    │
    ├── ToolNode(tools) + tools_condition → 보일러플레이트 제거
    ├── MemorySaver → thread_id별 대화 기억
    └── interrupt_before → 사람 승인 후 진행
```

### 주요 함수 I/O

| 함수 | 입력 | 출력 |
|---|---|---|
| `agent_node(state)` | AgentState(messages) | `{'messages': [AIMessage]}` |
| `tools_node(state)` | AgentState(messages[-1].tool_calls) | `{'messages': [ToolMessage, ...]}` |
| `should_continue(state)` | AgentState | `"tools"` 또는 `END` |
| `trim_node(state)` | TrimState(messages) | `{'messages': [RemoveMessage, ...]}` |

## 고려사항 & 질문 모음

1. **State 전체 반환 vs 변경된 키만 반환**: `return state` 대신 `return {'score': new_score}` 패턴 사용. 전체 반환은 그래프 확장 시 의도치 않은 덮어쓰기 발생 가능.

2. **MemorySaver의 한계**: 인메모리 저장이므로 프로세스 종료 시 데이터 유실. 프로덕션에서는 Redis/PostgreSQL 기반 checkpointer 사용 필요.

3. **interrupt_before 노드 선택**: `['tools']`가 가장 일반적(LLM 판단은 했지만 실행 전 확인). `['agent']`는 LLM 호출 자체 전에 멈추므로 사용 빈도 낮음.

4. **add_messages vs operator.add**: add_messages는 같은 ID 메시지 교체 기능 있음. 단순 로그 누적이면 operator.add가 적합.

5. **그래프 시각화**: `app.get_graph().draw_mermaid_png()`로 노드/엣지 구조를 시각적으로 확인 가능. 디버깅 시 활용.
