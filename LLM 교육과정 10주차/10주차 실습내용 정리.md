## 핵심 개념 상세 정리

### 10-1. 파인튜닝 필요성 — 프롬프트/RAG의 한계

에이전트가 엇나가는 4가지 문제:

| 문제 | 증상 | 해결 방향 |
|---|---|---|
| 출력 포맷 흔들림 | JSON/Markdown 구조 깨짐 | 파인튜닝 |
| 말투 불일관 | 존댓말/반말 혼용 | 파인튜닝 |
| 분류 오류 | 의도 분류 정확도 부족 | 파인튜닝 |
| 프롬프트 비대화 | 시스템 프롬프트 지나치게 길어짐 | 파인튜닝으로 내재화 |

| 해결책 | 적용 시점 |
|---|---|
| 프롬프트 엔지니어링 | 행동 지침, 출력 형식 지정 |
| RAG | 외부 지식이 필요한 경우 |
| 파인튜닝 | 프롬프트/RAG로 해결 안 되는 행동·포맷·어투 일관성 |

### 10-2. 파인튜닝 종류 — Full FT, LoRA, QLoRA

| 방식 | 학습 파라미터 | 특징 |
|---|---|---|
| Full Fine-tuning | 전체 | 성능 최고, 비용·메모리 최대 |
| LoRA | 저랭크 행렬(A·B) | 원래 가중치 동결, 작은 행렬만 학습 → 메모리 절약 |
| QLoRA | 저랭크 행렬 + 양자화 | 4bit 양자화로 추가 메모리 절감 |

#### LoRA 원리

- 원래 가중치 행렬 W를 동결
- 저랭크 행렬 A(d×r), B(r×d)를 학습 (r << d)
- 추론 시: W' = W + A×B

#### 파인튜닝을 위한 2가지 질문

1. **얼마나 바꾸나** — 학습할 파라미터 범위 결정 (Full FT vs PEFT vs QLoRA)
2. **무엇으로 가르치나** — 학습 데이터 품질과 양

### 10-3. OpenAI Fine-tuning API — 4단계 파이프라인

```
1. 데이터 준비(JSONL) → 2. 파일 업로드 → 3. Job 생성·실행 → 4. 모델 평가
```

### 10-6. 문서 파싱 — unstructured 라이브러리

- PDF, HTML, DOCX, PPTX 등 다양한 형식 지원
- `partition()` 함수로 문서를 element 단위로 분해

| 전략 | 속도 | 정확도 | 설명 |
|---|---|---|---|
| `fast` | 빠름 | 보통 | 텍스트 추출만 |
| `hi_res` | 느림 | 높음 | detectron2/yolox 기반 레이아웃 인식 |

#### element 카테고리

| 카테고리 | 설명 |
|---|---|
| `Title` | 제목/헤더 |
| `NarrativeText` | 본문 텍스트 |
| `Table` | 표 |
| `Header` / `Footer` | 머리말/꼬리말 |
| `ListItem` | 목록 항목 |

#### 메타데이터

- `page_number`, `filename`, `filetype`
- `coordinates`: 각 element의 페이지 내 좌표
- `pageindex` 라이브러리로 document hierarchy 파악

### 10-7. 청킹 전략 — chunk_by_title, 적응형 청킹

| 방식 | 설명 | 주요 파라미터 |
|---|---|---|
| `chunk_by_title` | 제목 기준으로 분할 | `max_characters`, `new_after_n_chars`, `combine_text_under_n_chars` |
| `chunk_elements` | 크기 기반 분할 | overlap 지원 |
| `adaptive_chunk` | 평균 텍스트 길이에 따라 자동 조정 | 200자↑→1000, 50~200→500, 50↓→300 |

```python
def adaptive_chunk(elements) -> list:
```

## 코드 흐름 정리

```
[1-2차시: 파인튜닝]
문제 정의 (프롬프트 한계) → 파인튜닝 방식 선택 (Full FT / LoRA / QLoRA)
    │
    ├── OpenAI Fine-tuning
    │   학습 데이터 작성(JSONL) → validate/check_sample → filter_clean
    │   → 데이터 증강(make_augment_prompt) → split_jsonl(train/val)
    │   → upload_jsonl → build_job_payload → Job 실행 → 평가
    │
    └── HuggingFace LoRA
        LoraConfig(r=16, target_modules=[q,k,v,o]) → get_peft_model
        → SFTTrainer(model, train_ds, eval_ds) → trainer.train()

[3-4차시: 문서 처리]
PDF 입력 → partition(strategy='fast'/'hi_res') → element 분류
    │
    ├── 텍스트 처리: clean → chunk(by_title / elements / adaptive) → FAISS RAG
    ├── 테이블 처리: PyMuPDF/Camelot 추출 → clean_table → table_to_markdown
    └── 이미지 처리: base64 인코딩 → VisionOCR → Document 변환
```

## 고려사항 & 질문 모음

1. **파인튜닝 vs 프롬프트 엔지니어링**: 파인튜닝은 비용(학습 데이터 준비, API 비용, 시간)이 크므로 프롬프트 엔지니어링 → RAG → 파인튜닝 순서로 시도하는 것이 효율적.

2. **LoRA r값 선택**: r이 작을수록 파라미터 절약이 크지만 표현력 감소. 실습에서는 r=16 사용. 일반적으로 r=8~64 범위에서 태스크 복잡도에 따라 선택.

3. **데이터 검증의 중요성**: 토큰 초과, 중복 user 메시지, 필수 role 누락 등이 있으면 파인튜닝 실패하거나 성능 저하. `validate()` → `filter_clean()` 파이프라인 필수.

4. **unstructured strategy 선택**: `fast`는 텍스트만 추출하므로 표/이미지가 중요한 문서에는 `hi_res` 필요. 단, `hi_res`는 detectron2/yolox 의존성이 있어 환경 설정이 복잡.

5. **테이블 추출 도구 비교**: PyMuPDF는 범용적이고 빠르지만 비격자 표 정확도가 낮을 수 있음. Camelot은 격자 표에 강하지만 Ghostscript 의존. 문서 특성에 따라 선택.

6. **멀티모달 RAG**: 텍스트 + 테이블(Markdown 변환) + 이미지(Vision OCR)를 모두 Document로 통합하면 하나의 FAISS 인덱스로 멀티모달 검색 가능. 실무에서는 각 타입별 메타데이터를 잘 관리해야 함.
