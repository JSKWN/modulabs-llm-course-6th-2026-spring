## 핵심 개념 상세 정리

### 12-1. Naive RAG의 한계 (multi-hop 추론)

청크 → 임베딩 → 벡터 검색 → LLM 답변의 기본 RAG는 "한 청크 안에 답이 있는" 질문엔 강하나, 여러 관계를 거치는 multi-hop 질문엔 약함.

- 예: "A의 멘토가 쓴 논문 제목은?" → A·멘토·논문이 서로 다른 청크에 흩어져 있으면 단일 검색으로 연결 불가
- `multihop_diagnosis()`로 임베딩 검색이 중간 단계를 놓치는 현상을 진단

> 실무: 임베딩은 의미적 유사도를 보지만 "관계의 연쇄"는 표현하지 못함. 이 한계가 GraphRAG의 동기

### 12-2. 지식 그래프 기초 (networkx)

엔티티를 노드, 관계를 방향 엣지로 표현함.

```python
import networkx as nx
G = nx.DiGraph()
G.add_edge('모리카이 센', '탈라미르 헤쉬', relation='mentored_by')
list(G.successors('모리카이 센'))      # 진출 이웃
nx.all_simple_paths(G, src, tgt, cutoff=3)  # multi-hop 경로
```

- 노드 유형: Person, Organisation, Product, Concept, Publication
- `successors`·`predecessors`로 이웃, `all_simple_paths`로 multi-hop 경로 탐색

### 12-3. LLM 엔티티·관계 추출 (JSON 스키마)

LLM에 추출 스키마를 지시해 텍스트에서 엔티티·관계를 JSON으로 받음. Pydantic으로 타입을 강제하면 더 안정적.

```python
class Entity(BaseModel):
    name: str
    type: Literal["Person", "Organisation", "Product", "Concept"]

class ExtractedKG(BaseModel):
    entities: list[Entity]
    relations: list[Relation]

structured_llm = llm.with_structured_output(ExtractedKG)
```

- `strip_code_fence()`로 코드펜스 제거 후 `json.loads`
- `json_to_graph(data)`로 추출 결과를 `nx.DiGraph`로 변환

### 12-4. 엔티티 정규화 (별칭 통합)

같은 대상의 다른 표현("센" vs "모리카이 센")을 하나로 합침.

```python

    # 짧은 이름이 긴 이름의 부분 문자열이면 별칭으로 간주해 통합

               if short != long and len(short) < len(long) and short in long}
    ...  # 별칭을 대표 노드로 합치고 자기 루프·중복 엣지 제거
```

> 실무: 추출 단계에서 같은 엔티티가 여러 표기로 나오면 그래프가 분절됨. 정규화로 노드를 통합해야 경로 탐색이 정확해짐

### 12-5. 관계 기반 multi-hop 질의

정제된 그래프에서 경로를 따라 답을 찾음.

- `find_relation(G, e1, e2, max_hops)`: 두 엔티티 사이 최단 경로
- `explain_relation(G, e1, e2)`: 경로를 엣지 라벨과 함께 설명
- `kg_to_text(G, focus_nodes, question)`: 관련 노드의 이웃 관계를 텍스트로 직렬화해 LLM 컨텍스트로 제공

### 12-7. 엣지 가중치와 출처 추적

```python
def add_edge_weights(G):
    for u, v, d in G.edges(data=True):
        d['weight'] = len(d.get('source_chunks', []))   # 출처 청크 수 = 중요도
    return G
```

- 여러 청크에서 반복 등장하는 관계일수록 가중치가 높음
- `source_chunks` 덕분에 검색 시 원본 청크를 되불러와 근거로 제시 가능

### 12-8. Leiden 커뮤니티 탐지

밀집 연결된 엔티티 그룹(주제 단위)을 자동 분할함.

```python
from graspologic.partition import leiden
def detect_communities(G):
    partitions = leiden(G.to_undirected())   # 무방향 변환 후 Leiden
    communities = defaultdict(list)
    for node, cid in partitions.items():
        communities[cid].append(node)
    return dict(communities)
```

> 실무: 커뮤니티 = 코퍼스의 "주제 그룹". 글로벌 검색에서 주제 단위 요약의 근거가 됨

### 12-9. 커뮤니티 요약

각 커뮤니티의 엔티티·관계 목록을 LLM에 넘겨 4~6문장 요약을 생성함.

```python
def summarize_community(G, nodes) -> str:
    ent_lines = [f"- {n} ({G.nodes[n].get('type','?')})" for n in nodes]
    rel_lines = [f"- {u} --[{rel}]--> {v}" for u, v, d in G.edges(data=True)
                 if u in nodes and v in nodes for rel in (d.get('relations') or [''])]
    return llm.invoke(SUMMARY_PROMPT.format(entities=..., relations=...)).content
```

- 인덱스(그래프·커뮤니티·요약·청크)는 `pickle`로 저장/로드해 검색 단계와 분리

### 12-11. 글로벌 검색 (Global Search)

코퍼스 전체의 주제·경향 같은 거시 질문에 답함.

```python
def global_search(question, index) -> str:
    all_summary = '\n\n'.join(f"[C{cid}]\n{s}" for cid, s in index['summaries'].items())
    # 모든 커뮤니티 요약을 종합해 LLM이 통합 답변 생성
    return llm.invoke([sys, HumanMessage(content=f"질문: {question}\n\n{all_summary}")]).content
```

- 개별 엔티티가 아니라 주제 단위 커뮤니티 요약에 기반

### 12-12. MS GraphRAG 패키지

직접 구현한 파이프라인을 Microsoft `graphrag`가 자동화함.

```bash
graphrag init  --root {ROOT}             # 프로젝트 초기화(YAML·.env)
graphrag index --root {ROOT}             # 자동 9단계 파이프라인 실행
graphrag query --root {ROOT} --method local|global "{질문}"
```

- 9단계: 문서 로드 → text unit → 그래프 추출 → finalize → covariate → 커뮤니티 생성(Leiden) → text unit 정리 → 임베딩 생성
- Gleaning(`extract_graph.max_gleanings`): 반복 추출로 깊이 향상 (gleaning 0 → 18 엔티티, gleaning 2 → 21 엔티티)
- 출력 아티팩트(parquet): `entities`, `relationships`, `community_reports`, `text_units`, `documents`
- `to_networkx(arts)`로 그래프 복원, `top_entities()`로 degree 기준 핵심 엔티티 분석

> 실무: 학습 목적엔 직접 구현(3차시)이 좋고, 운영엔 `graphrag` 패키지가 캐싱·재현성·커뮤니티 보고서까지 제공해 효율적

## 코드 흐름 정리

```
[1차시: Naive RAG 한계 → 그래프 기초]
청크 → build_vector_store → retrieve → naive_rag (multi-hop 실패 시연)
networkx DiGraph → successors/predecessors → all_simple_paths

[2차시: 단일 문서 KG]
텍스트 → extract_graph(LLM, Pydantic) → json_to_graph → resolve_entities
       → answer_via_kg / find_relation / explain_relation / kg_to_text

[3차시: 코퍼스 파이프라인]
코퍼스 → extract_all_chunks → merge_chunk_results(source_chunks) → resolve_entities → add_edge_weights
       → detect_communities(Leiden) → summarize_community → save_index(pickle)
       → local_search(엔티티→이웃→청크) / global_search(커뮤니티 요약 종합)

[4차시: MS graphrag]
graphrag init → index(9단계, Gleaning) → parquet 아티팩트 → to_networkx / query(local|global)
```

## 고려사항 & 질문 모음

1. **언제 GraphRAG가 필요한가**: 단일 청크로 답하는 사실 질의는 Naive RAG로 충분. 여러 엔티티·관계를 연결해야 하는 multi-hop 질의, 또는 코퍼스 전체 주제를 묻는 거시 질의에서 GraphRAG가 우위.

2. **로컬 vs 글로벌 검색 선택**: 특정 엔티티 중심 질문("X와 Y의 관계?")은 로컬 검색(엔티티 매칭 → 이웃). 코퍼스 전반 질문("주요 연구 주제는?")은 글로벌 검색(커뮤니티 요약 종합). 질문 유형에 따라 라우팅 필요.

3. **엔티티 정규화의 중요성**: 추출 단계에서 같은 대상이 여러 표기로 나오면 그래프가 분절돼 경로 탐색이 실패. 부분 문자열 별칭 통합 같은 정규화가 그래프 품질을 좌우.

4. **source_chunks(출처 추적)의 역할**: 노드·엣지에 출처 청크를 기록하면 검색 시 원본 텍스트를 근거로 되불러올 수 있음. 가중치 계산과 답변 근거 제시 모두에 활용.

5. **Leiden 커뮤니티의 의미**: 커뮤니티는 코퍼스의 주제 그룹에 해당. 글로벌 검색은 이 커뮤니티 요약을 종합하므로, 커뮤니티 품질이 거시 질의 정확도에 직접 영향.

6. **직접 구현 vs graphrag 패키지**: 직접 구현(3차시)은 동작 원리 학습에 적합. Microsoft `graphrag`는 자동 파이프라인·캐싱·커뮤니티 보고서·Gleaning을 제공해 운영에 유리하나, 내부 동작은 블랙박스에 가까움. Gleaning 횟수는 추출 깊이와 비용의 트레이드오프.

7. **LangGraph와 Graph RAG 구분 (이름 혼동 주의)**: 둘 다 "graph"가 들어가지만 가리키는 대상이 다름. LangGraph(8주차)의 그래프는 앱의 실행·제어 흐름(노드=함수 단계, 엣지=전이), Graph RAG(12주차)의 그래프는 지식 구조(노드=엔티티, 엣지=관계)임. 경쟁이 아니라 층위가 달라 결합도 가능(예: 질문 분류 후 local/global 분기를 LangGraph 조건부 엣지로 구현).

| 구분 | LangGraph | Graph RAG |
|---|---|---|
| "그래프"의 정체 | 앱 실행·제어 흐름 | 지식(데이터) 구조 |
| 노드 / 엣지 | 함수 단계 / 전이 | 엔티티 / 관계 |
| 푸는 문제 | 앱 오케스트레이션(어떻게 실행할지) | 검색·추론(무엇을 찾을지) |
| 층위 | 애플리케이션 제어 | 데이터·검색 |
| 대표 도구 | LangChain LangGraph | networkx, graspologic(Leiden), MS graphrag |
| 배운 주차 | 8주차 | 12주차 |
